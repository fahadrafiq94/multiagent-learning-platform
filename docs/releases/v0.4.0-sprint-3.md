# FREDi Sprint 3 — Semantic Multi-Agent Orchestration

## 1. Sprint objective

Sprint 3 replaced FREDi's primary static keyword routing with an LLM-based semantic Orchestrator Agent while preserving the original deterministic router as a recovery mechanism.

The main problem was that real student messages do not reliably contain predefined routing keywords. A student may describe an AP+ navigation problem, a business-process reasoning problem, or a scenario-context problem using ordinary language that is not present in a fixed keyword list.

The sprint therefore introduced a routing architecture in which the system first determines the student's **meaning and immediate need**, and only falls back to deterministic keyword matching when semantic routing cannot provide a usable decision.

The resulting architecture also keeps agents stateless and reusable so the same agent instances can serve multiple students concurrently and later operate behind a vLLM inference service.

---

## 2. Previous architecture

Before Sprint 3, orchestration depended primarily on deterministic keyword matching.

Conceptually:

```text
Student message
      |
      v
Static keyword router
      |
      +--> Scenario Agent
      +--> Process Coach Agent
      +--> AP+ Navigator Agent
      `--> Fallback
```

This approach was predictable and easy to test, but it had an important limitation: routing quality depended on whether the student's wording matched a predefined set of phrases.

For example, a student might write:

> I already understand the business action. I just do not know how to record it in the software.

The intended destination is the AP+ Navigator Agent even though the message may not contain explicit phrases such as `AP+`, `screen`, `menu`, or `field`.

The same problem occurs for process reasoning and scenario-context questions.

---

## 3. New routing architecture

Sprint 3 introduced `OrchestratorAgent` as the primary semantic router.

The routing flow is now:

```text
Student message
      |
      v
OrchestratorAgent
      |
      +--> scenario
      +--> process_coach
      +--> ap_plus_navigator
      `--> fallback
              |
              v
     deterministic keyword fallback
              |
              +--> scenario
              +--> process_coach
              +--> ap_plus_navigator
              `--> clarification response
```

If the semantic model call itself fails, the same deterministic fallback is used.

This gives FREDi both semantic flexibility and deterministic fault recovery.

---

## 4. Orchestrator Agent

The Orchestrator Agent has one responsibility: classify the student's current message and select the specialist agent that is best able to handle the immediate need.

It does **not** answer the student's learning question itself.

### Supported routes

#### `scenario`

Used when the student's main need concerns the exercise or company context, including:

- company characteristics,
- the student's role,
- the business situation,
- the business problem,
- missing scenario facts,
- assumptions about the exercise context.

#### `process_coach`

Used when the student needs conceptual or business-process reasoning, including:

- why an action is required,
- what should logically happen next,
- what information is needed before continuing,
- relationships between business events and documents,
- procurement, sales, production, logistics, and related process reasoning.

#### `ap_plus_navigator`

Used when the student understands the business task but needs help performing it inside AP+, including:

- system navigation,
- screens,
- menus,
- buttons,
- fields,
- where information should be entered,
- system errors or interface problems.

#### `fallback`

Used only when there is genuinely insufficient information to determine the student's immediate need.

---

## 5. Structured semantic routing

Semantic routing uses a structured model response rather than parsing free-form model text.

The routing decision contains:

```text
route
reason
```

The supported route values are:

```text
scenario
process_coach
ap_plus_navigator
fallback
```

The provider-neutral `ModelChatRequest.response_schema` is translated by the Ollama provider into Ollama's structured-output `format` field.

This means the orchestration layer remains independent of Ollama-specific API details.

---

## 6. Deterministic keyword router as fallback

The original keyword router was intentionally retained.

It is no longer the primary routing mechanism.

It is used when:

1. the Orchestrator Agent returns `fallback`, or
2. the semantic model request fails.

The resulting policy is:

```text
semantic specialist route
    -> use specialist directly

semantic fallback
    -> deterministic keyword routing

semantic routing failure
    -> deterministic keyword routing

keyword fallback
    -> clarification response
```

This recovery path is deliberately conservative. The deterministic router is not intended to duplicate full semantic understanding.

---

## 7. Graph integration

The LangGraph topology keeps `route_request` as the routing node.

`OrchestratorAgent` is injected into the graph rather than being stored globally.

The graph contains the following main nodes:

```text
START
  |
prepare_input
  |
route_request
  |
  +--> scenario_agent
  +--> process_coach_agent
  +--> ap_plus_navigator_agent
  `--> fallback_response
          |
    finalize_response
          |
         END
```

The semantic Orchestrator operates inside the routing node; it is not represented as another specialist graph node because its role is routing, not student-facing execution.

---

## 8. Agent registry design

The specialist registry contains only student-facing agents:

```text
ScenarioAgent
ProcessCoachAgent
APPlusNavigatorAgent
```

`OrchestratorAgent` is intentionally not registered as a specialist.

This keeps two responsibilities separate:

```text
routing responsibility
    -> OrchestratorAgent

student-help responsibility
    -> specialist agents
```

---

## 9. Model-service architecture

All agents depend on the provider-neutral `ModelService` facade rather than directly depending on Ollama.

```text
Agent
  |
  v
ModelService
  |
  v
ModelProvider
  |
  +--> Ollama today
  `--> vLLM later
```

The current Sprint 3 configuration deliberately keeps **one provider and one shared ModelService**.

The service contains no student/session state. It delegates each request to the provider.

---

## 10. Per-agent model selection

Sprint 3 also added optional model overrides for each agent while keeping a single provider.

The configured models are:

```text
orchestrator_model
scenario_agent_model
process_coach_agent_model
ap_plus_navigator_model
```

Each value is optional.

When it is unset, the provider uses the global default:

```text
ollama_chat_model
```

This works because `ModelChatRequest` already supports:

```python
model: str | None
```

and the Ollama provider resolves the model as:

```python
request.model or self.chat_model
```

Therefore the architecture can support configurations such as:

```text
Orchestrator       -> small fast routing model
Scenario Agent     -> general instruction model
Process Coach      -> stronger reasoning model
AP+ Navigator      -> grounded instruction model
```

without changing the graph or provider abstraction.

For now all agents may continue using the same default model.

---

## 11. Single-provider decision

Sprint 3 intentionally keeps one model provider.

Current deployment:

```text
all agents
   |
   v
shared ModelService
   |
   v
OllamaModelProvider
```

If a future architecture needs different providers or different inference clusters per agent, multiple `ModelService` instances can be introduced at the composition/factory layer without redesigning the agents.

That work is deferred until it is actually required.

---

## 12. Multi-user and concurrency design

Agents are designed to be reusable across users.

Agent instances contain only stable dependencies/configuration such as:

```text
ModelService reference
model override
system instructions
```

They do not store mutable state such as:

```text
current student
current session
last user message
current conversation
```

Instead, session-specific information travels through request/state objects.

Conceptually:

```text
Student A ----\
Student B -----+--> shared orchestration service
Student C ----/          |
                         v
                    shared agents
                         |
                         v
                   ModelService
```

A concurrent smoke script uses `asyncio.gather()` to exercise multiple independent student requests against one shared orchestration service.

This validates the application architecture for future multi-user serving.

Actual inference batching, GPU scheduling, backpressure, and throughput management remain provider/inference-server responsibilities.

---

## 13. Ollama provider behavior

The current Ollama provider is asynchronous and supports:

- non-streaming generation,
- streaming generation,
- embeddings,
- health checks,
- retries,
- timeout handling,
- structured output,
- per-request model selection.

The provider currently creates an `httpx.AsyncClient` for individual HTTP operations.

This does not prevent concurrent application requests, but future production optimization should use a reusable async client/connection pool with explicit application lifecycle management.

That optimization is intentionally deferred from Sprint 3.

---

## 14. Future vLLM migration

The current abstraction was designed so the agents should not require major changes when Ollama is replaced by vLLM.

Expected migration path:

```text
Agent
  |
ModelChatRequest
  |
ModelService
  |
VLLMModelProvider
  |
vLLM inference server
```

The vLLM-specific provider will be responsible for translating provider-neutral requests into the inference server's API format.

Future infrastructure work may include:

- reusable connection pools,
- batching,
- request scheduling,
- GPU concurrency controls,
- backpressure,
- observability,
- multiple model deployments,
- model-specific endpoints.

These concerns remain outside specialist-agent logic.

## 17. Manual semantic-routing validation

A manual semantic smoke script was added to test realistic student messages against the actual configured model rather than mocked routing responses.

The evaluation deliberately used messages that avoided relying on the static keyword list.

Examples included intent such as:

```text
I understand the business action but do not know how to perform it in the ERP system.

I know what was entered but do not understand the business reason for doing it.

I need to understand who I am acting as and what situation the organisation is facing.
```

Once Ollama was running correctly, all semantic routing cases passed.

This confirmed that semantic routing solved the original keyword-matching limitation.

---

## 18. Failure-recovery validation

During manual validation, Ollama was initially unavailable.

This exposed and validated the designed recovery chain:

```text
semantic model unavailable
       |
       v
deterministic keyword fallback
       |
       +--> recover specialist route when possible
       `--> clarification when still unclear
```

The orchestration layer therefore remained controlled rather than crashing when the semantic provider was unavailable.

## 19. Architectural decisions

### Decision 1 — semantic routing first

The LLM Orchestrator is the primary routing mechanism because student language cannot be represented reliably by a fixed keyword list.

### Decision 2 — keep deterministic routing

The deterministic router remains valuable as a predictable failure-recovery mechanism.

### Decision 3 — do not create a second `AgentRouter` abstraction

Routing already has clear ownership in the orchestration routing node plus `OrchestratorAgent`; another router abstraction would add unnecessary indirection.

### Decision 4 — Orchestrator is not a specialist agent

The Orchestrator classifies messages; it does not provide student-facing guidance.

### Decision 5 — dependency injection instead of global objects

The Orchestrator and registry are injected into graph construction, improving testability and avoiding mutable global state.

### Decision 6 — one provider for now

A single shared provider keeps the current infrastructure simple. Model selection can already vary per request.

### Decision 7 — per-agent model configuration belongs at composition/configuration level

The graph should not know which model an agent uses.

### Decision 8 — student/session state belongs in request/state objects

Agents remain reusable and safe for concurrent users.

### Decision 9 — defer transport optimization

Reusable HTTP connection pools and production inference optimization will be addressed with the vLLM/infrastructure work rather than mixed into Sprint 3 orchestration changes.

                      | Orchestrator Agent |

                                |

All model-backed components use:

```text

                           |
                           v

                           |

```

Each agent can optionally specify a model in its provider-neutral request while sharing the same provider.
