# FREDi Sprint 4 — Context Engineering v0.5.0

## 1. Sprint objective

Sprint 4 built the identity, state, conversation, context, onboarding,
controlled-update, and multi-user-safe foundations that FREDi needs before
retrieval-augmented generation (Sprint 5).

After Sprint 3, the system could route a student message to the right
specialist agent — but every agent was effectively conversationally
stateless. The system did not yet know:

- who the student is (identity),
- what the student is working on (current objective, process phase, AP+
  step, active blocker),
- what happened earlier in the conversation (bounded history),
- which business scenario the student is exercising (ScenarioCard),
- how much help the student should be given right now (guidance level),
- or how to observe and measure any of it (observability).

Sprint 4 therefore introduced the durable context layer:

```text
HTTP request
    → resolve external student identity → internal user_id
    → persist the student's message in the full conversation archive
    → ContextService builds a bounded AgentContext
    → onboarding gate or semantic routing
    → specialist agent (bounded context in, structured output out)
    → agent may propose state updates; application code persists them
    → guidance signal recorded, summary maybe updated, response finalized
```

The sprint's central guarantee:

> Persistent state lives in repositories and services, never in agents.
> The full conversation archive is stored, but only a bounded,
> token-budgeted context ever reaches the model. Agents remain stateless
> and reusable so many students can share the same agent instances.

---

## 2. Previous architecture

After Sprint 3, orchestration looked like this:

```text
Student message
      |
      v
LangGraph: prepare_input → route_request → specialist → finalize
```

The graph carried request/response state, but there was no:

- user identity model (student identity came in with the request and was
  not resolved or stored),
- session model or conversation archive,
- structured per-session state (objective, phase, step, blocker),
- scenario onboarding flow,
- context budgeting or history bounding,
- guidance policy,
- or per-request observability events.

That was sufficient to prove semantic routing, but not sufficient for a
multi-user learning environment where a student's work must survive
across turns and requests.

---

## 3. Core architectural decisions

### Decision 1 — Memory ≠ State ≠ Knowledge

The sprint kept three concepts strictly separate:

```text
State
    → authoritative structured runtime information
    (current objective, process phase, current step, active blocker)

Memory / conversation archive
    → what happened in prior interactions
    (messages, later summaries)

Knowledge
    → external AP+ / Process Coach material
    (Sprint 5 RAG)
```

They are never merged into a generic "memory" object. State is
authoritative; memory is recall; knowledge is grounding.

### Decision 2 — State lives outside agents

Agents receive a bounded `AgentContext`, reason, and return structured
output (optionally with state-update proposals). They never own, mutate,
or persist state. This is what makes agents safe to share across
concurrent users and safe to reuse behind future vLLM serving.

### Decision 3 — Full archive, bounded prompt

The complete conversation archive is always stored. Model requests never
see the full archive — they see a bounded, token-budgeted recent suffix
selected by the ContextBudgetService (plus, from 4B.8, a compact session
summary when one exists).

### Decision 4 — LLMs propose; application code persists

Specialist agents may propose controlled session-state updates, but only
through a typed `state_update_proposal`. Application code validates the
proposal against an allow-list of fields per agent role and persists it
with optimistic version checking. Agents cannot touch protected fields
(ids, ownership, versions, timestamps, onboarding internals, summaries).

### Decision 5 — Provider independence

None of the context, state, repository, or orchestration layers depend on
Ollama. Token estimation is provider-neutral, and the model boundary
remains the Sprint 1/2 provider abstraction so later vLLM deployment does
not require redesigning this layer.

### Decision 6 — Repository contracts before storage

Storage sits behind repository contracts. The current implementation is
in-memory (with `asyncio` locks, optimistic versioning, and deep copies),
chosen for deterministic development and testing. PostgreSQL (later, with
pgvector) is a storage implementation behind the same contracts — agent
and service behavior must not change.

---

## 4. Identity and multi-user isolation

External student identity is resolved to an internal user:

```text
app/identity/schemas.py     → UserIdentity (student_id → user_id)
app/repositories/identity.py → identity repository contract
```

Every context, state, and conversation operation is keyed by
`(user_id, session_id)`, and ownership is validated at the service layer:
a session must belong to the requesting user, and cross-user access is
rejected. Isolation is not a promise — it is enforced and tested (see
Section 16).

---

## 5. Repositories and in-memory persistence

```text
app/repositories/
    identity.py      identity contract
    context.py       session/user context, conversation, session contracts
    in_memory.py     in-memory implementation
    exceptions.py    DuplicateRecordError, RepositoryNotFoundError,
                     VersionConflictError
```

The in-memory implementation is concurrency-ready by construction:

- per-repository `asyncio.Lock`s serialize mutating operations;
- versioned saves are optimistic — a save with a stale
  `expected_version` raises `VersionConflictError`;
- every read and write crosses the boundary as a deep copy, so callers
  can never alias or mutate stored state.

`create_in_memory_repositories()` is the composition entry point used by
the runtime factory and the test suite.

## 6. State model

### 6.1 UserContext

Longer-lived user-level context (`app/services/user_context_service.py`):
learning-profile information and shared guidance state, including the
`HintState` counters used by the 4B.9 guidance policy.

### 6.2 SessionContext

Authoritative mutable session state
(`app/services/session_context_service.py`):

- `current_objective`,
- `current_process_phase`,
- `current_step_id`,
- `active_blocker`,
- `unresolved_questions`,
- `last_selected_agent` (written deterministically by the application),
- onboarding lifecycle state,
- the persisted session summary (4B.8).

All updates go through `SessionContextService.update(expected_version=…)`
with optimistic conflict checking.

### 6.3 Conversation archive

`app/services/conversation_service.py` stores every message. Creating a
session seeds both the `ConversationSession` and its initial
`SessionContext`. The archive supports bounded batched fetches
(`get_history(offset, limit)`, recent-message listing, counts) — the
bounded fetches are what feed context building and summary updates; the
archive itself is never truncated.

### 6.4 ScenarioCard and onboarding

`app/services/scenario_card_service.py` owns the per-user business
scenario (company context, learner role, business problem, goals,
constraints). `app/services/scenario_onboarding_service.py` tracks the
onboarding lifecycle (`NOT_STARTED → COLLECTING → REVIEWING → CONFIRMED`)
and exposes the runtime gate: a user without a confirmed ScenarioCard is
routed through scenario onboarding before specialist routing.

---

## 7. ContextService and bounded AgentContext

`app/services/context_service.py` is the single place where bounded
agent context is assembled:

1. validate user/session ownership;
2. load/create the user context;
3. load the required session context;
4. fetch bounded recent-message candidates from the archive;
5. exclude the just-persisted current message where it is already stored;
6. serialize essential sections and apply the context budget (4B.7);
7. include the session summary when one exists (4B.8);
8. select the guidance level centrally via `select_guidance()` (4B.9) and
   record `guidance_reason` in the metadata;
9. return an `AgentContext` with real `ContextMetadata` observability
   values.

`ContextMetadata` exposes the context build to callers and observability:
`included_sections`, `recent_message_count`, `candidate_message_count`,
`dropped_message_count`, `estimated_input_tokens`,
`input_token_budget`, `truncation_applied`, `summary_included`,
`guidance_reason`, and more.

`ContextService.build()` keeps an optional per-request
`recent_message_limit` that overrides the configured candidate cap for
that request only.

---

## 8. Shared guidance domain and agent-specific policies (4B.1–4B.2)

The `GuidanceLevel` domain lives in `app/domain/guidance.py` and is shared
by the context layer, the agents, and the guidance policy. Each specialist
has its own context policy (`app/context/policies.py`,
`app/agents/policies.py`, `app/agents/context_prompt.py`) controlling how
context sections are rendered for that role — but no agent decides the
guidance level.

---

## 9. Structured scenario onboarding (4B.3–4B.4)

Onboarding is a workflow around the Scenario Agent, not a separate agent:

```text
ScenarioAgent.extract_draft()     → structured scenario extraction
ScenarioAgent.assess_review()     → semantic CONFIRM / CORRECT / REJECT / UNCLEAR
ScenarioAgent.merge_extraction()  → deterministic merge of onboarding data
```

`app/services/scenario_onboarding_interaction_service.py` drives the loop;
`app/services/scenario_card_service.confirm_draft()` finalizes the
ScenarioCard. The model only fills semantic fields; ownership, versions,
and lifecycle state are application-controlled.

---

## 10. LangGraph context integration (4B.5)

The orchestration graph now:

- loads context first (`load_context` node: resolves identity, persists
  the user message, builds the `AgentContext`);
- applies the onboarding gate (users without a confirmed ScenarioCard go
  through the scenario-onboarding path; confirmed users go to semantic
  routing);
- passes the bounded `AgentContext` to the selected specialist instead of
  letting any node reconstruct context.

The graph remains checkpointer-free — all persistence happens in the
nodes' service calls, which is what keeps concurrent executions
independent.

---

## 11. Controlled state updates (4B.6)

```text
SpecialistAgentOutput.state_update_proposal
      |
      v
apply_state_updates node
      |
      v
SessionStateUpdateService (field allow-list per agent role)
      |
      v
SessionContextService.update(expected_version=…)
```

Each proposal operation is typed (`SessionStateUpdateOperation`: field,
action, value, reason) in `app/context/state_updates.py`. Allowed fields
per role (e.g. `current_step_id` only for the AP+ Navigator,
`current_process_phase` only for role-appropriate agents) are enforced in
application code. The read-modify-write is version-checked; a conflicting
write degrades best-effort (recorded in response metadata) and never
breaks the student's turn.

---

## 12. Context budgeting (4B.7)

```text
ApproximateTokenEstimator   app/context/token_estimator.py
ContextBudgetPolicy         app/context/budget.py
ContextBudgetService        app/context/budget.py
```

The estimator is provider-neutral (character-based with per-message
overhead). The policy protects essential context first — current message,
ScenarioCard, SessionContext, profile state — and only recent history may
be dropped. Selection guarantees:

- configured hard message-count cap,
- token-budget cap,
- newest messages preferred,
- chronological order preserved,
- the selected history is a contiguous recent suffix (a newer message that
  does not fit is never skipped to admit older ones),
- the stored archive is untouched.

Settings: `CONTEXT_MAX_TOKENS`, `CONTEXT_RESERVED_OUTPUT_TOKENS`,
`CONTEXT_MAX_RECENT_MESSAGES`, `CONTEXT_CHARACTERS_PER_TOKEN`,
`CONTEXT_MESSAGE_OVERHEAD_TOKENS`.

---

## 13. Session summaries (4B.8)

Long conversations must not lose all semantic information when old raw
messages fall out of the recent window.

- `SessionSummaryService.maybe_update()` updates only after
  `context_summary_min_new_messages` have fallen out of the recent window
  (deterministic `should_update_summary` policy);
- the update is incremental: a bounded batch of the messages that just
  aged out is fetched (the full archive is never loaded, old messages are
  never re-sent raw);
- the model fills semantic fields only (`app/context/summary_prompt.py`:
  `SummaryDraft`, `build_summary_request`, `sanitize_summary_draft`) —
  ids, counts, and timestamps are application-owned and drafts are
  validated and bounded;
- the summary is persisted in session state and included in
  `AgentContext` with `summary_included` recorded;
- the `update_session_summary` graph node runs on the specialist and
  fallback paths (scenario onboarding bypasses it) and all summary
  failures — model error, invalid output, version conflict — are
  contained: the previous summary is kept and the turn never breaks.

Settings: `SUMMARY_MODEL`, `CONTEXT_SUMMARY_MIN_NEW_MESSAGES`,
`CONTEXT_SUMMARY_MAX_ITEMS_PER_LIST`, `CONTEXT_SUMMARY_MAX_OVERVIEW_CHARS`.

## 14. Guidance policy (4B.9)

Guidance level is selected centrally and deterministically — the LLM never
sets it.

- each specialist's **existing** structured output now carries a
  `StudentResponseAssessment` (closed enum: correct / partially_correct /
  incorrect / off_track / not_applicable, plus
  `misconception_detected`, `reason`). A tolerant validator degrades
  malformed assessments to `None`, so a broken judgment can never fail
  the student's turn;
- the same assessment rubric (`RESPONSE_ASSESSMENT_INSTRUCTIONS` in
  `app/agents/policies.py`) is embedded in all three specialist system
  prompts — zero extra inference;
- a new `record_response_signal` graph node maps the assessment to bounded
  counter movements on `HintState` (`consecutive_unproductive_attempts`,
  `successful_independent_steps`) via `assessment_signal()` — the raw
  LLM assessment is never persisted;
- `app/domain/guidance_policy.py` — pure `select_guidance()` returning
  `GuidanceDecision(level, reason)`: manual-override pin → baseline →
  blocker floor (streak 1/2/≥3 → GUIDED/DIRECTED/EXPLICIT) → struggle
  floor (≥2 unproductive → DIRECTED, ≥3 → EXPLICIT) → productive-reasoning
  de-escalation (exactly one step down, MINIMAL floor);
- `ContextService.build()` selects the level and records
  `guidance_reason` in `ContextMetadata`.

Core rule: help escalates only as needed; productive student reasoning
is preserved.

## 15. Observability (4B.10)

One typed event per orchestration request, local-first, no cloud tracing
dependency:

- `RequestObservabilityEvent` (frozen pydantic, `extra="forbid"`) plus a
  pure `build_request_event(state, *, duration_ms)` mapper in
  `app/observability/events.py`; missing data degrades to `None` fields
  and the mapper never raises;
- carries request/session identifiers, outcome + error, route/reason,
  selected agent, onboarding flag, guidance level/reason,
  context-budget metrics, candidate/selected/dropped counts, truncation,
  summary-update fields, accepted/rejected state-update counts, response
  signal fields, model/provider name, model latency, and request
  `duration_ms`;
- emitted by `OrchestrationService.execute()` on both success and
  graph-error paths via the dedicated `fredi.request_events` logger —
  best-effort, so an observability failure can never fail or mask the
  request;
- never carries user message content, assistant content, or free-text LLM
  output;
- optional research export: `OBSERVABILITY_LOG_FILE` (default off) writes
  one JSON object per line via a `FileHandler` on the same logger.

The event schema is designed to persist unchanged into a future
`research_events` table; RAG retrieval references/scores (Sprint 5) will
be added to the same shape.

## 16. Multi-user and concurrency validation (4B.11)

Sprint 4B.11 proved the shared-runtime architecture under real
interleaving with deterministic in-repo tests (no new dependency, no
wall-clock assertions, no network):

```text
tests/concurrency/test_repositories.py   (layer A — repository races)
    concurrent duplicate creation → exactly one winner, rest
    DuplicateRecordError
    lost-update checks on UserContext / SessionContext →
    VersionConflictError, version advances exactly by applied writes
    concurrent appends → nothing lost
    cross-user reads during writes → never leak
    reads return complete deep copies (no aliasing)

tests/concurrency/test_orchestration.py  (layer B — shared runtime)
    one shared OrchestrationRuntime serves 4 students × 2 requests
    canary cross-user leakage checked at response, captured-model-prompt,
    and conversation-archive level
    one user / two concurrent sessions → no cross-session bleed
    simultaneous state updates on one session → coherent (a conflict
    degrades a state write, never the student's turn; no lost update)
    concurrent ContextService builds → isolated AgentContexts
    agent registry serves single stateless instances
    concurrent 4B.9 signal writes → hint-state counters stay bounded

tests/integration/test_orchestration_api.py (layer C — HTTP)
    concurrent POST /orchestration/invoke → wire-level per-student
    isolation asserted on the response body
```

All interleaving is forced with exact `asyncio.Event` barriers;
assertions cover counts, versions, and canary absence — never timing or
completion order. The expected outcome from code inspection was confirmed:
**zero runtime defects** — the lock-protected, version-checked,
deep-copying architecture was already concurrency-ready, and the tests
now guarantee that stays true. This is the security evidence that
user/session isolation holds under load, and the architecture assertion
that one agent instance per role can serve all students (vLLM batching
readiness).

## 19. Architectural decisions (summary)

1. **State outside agents** — repositories/services own all mutable
   state; agents are stateless and shared.
2. **Memory ≠ State ≠ Knowledge** — separate stores, separate services.
3. **Full archive, bounded prompt** — token budget protects essential
   context; only history is droppable; contiguous recent suffix.
4. **LLMs propose, app persists** — typed, allow-listed, version-checked
   state updates; protected fields are app-only.
5. **Provider-neutral estimation** — budgeting independent of Ollama,
   ready for vLLM.
6. **Repository contracts now, SQL later** — in-memory implementation is
   the deterministic dev/test backend; PostgreSQL+pgvector lands behind
   the same contracts in the persistence/RAG sprint.
7. **Onboarding is a workflow, not an agent** — structured lifecycle
   around the existing Scenario Agent.
8. **Guidance is deterministic** — counters and policy decide the level;
   the LLM only judges the student's response inside the call it already
   makes (zero extra inference).
9. **Observability is best-effort and content-free** — one typed event
   per request; it can never fail or mask a student's turn; no
   message/LLM free-text content.
10. **Concurrency proven, not assumed** — barrier-forced interleaving
    with canary leakage checks at four layers (repository, captured
    prompt, response, HTTP wire).

  stable);

  runtime) but not deployed.
