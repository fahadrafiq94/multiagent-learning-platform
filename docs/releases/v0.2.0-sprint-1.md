# Sprint 1 Release Report

**Version:** v0.2.0

**Sprint:** Sprint 1 – Model Service

**Status:** Completed

**Date:** August 2026

---

# Overview

Sprint 1 focused on implementing the Model Service layer for the FREDi Multi-Agent Learning Platform.

The objective of this sprint was to create a unified abstraction between the application and any language model provider. This ensures that future orchestration, agents, context engineering, and RAG components do not communicate directly with Ollama or any other inference backend.

By the end of this sprint, the backend can communicate with a local Ollama model provider through a provider-independent Model Service interface. The architecture is prepared for future migration to vLLM without requiring changes to agent or orchestration logic.

This sprint intentionally did not implement LangGraph workflows, agents, context engineering, RAG, PostgreSQL integration, or frontend functionality. Those areas belong to later sprints.

# Implemented Components

## Model Service Architecture

A provider-independent Model Service architecture was implemented.

The Model Service is now the single application-facing layer for model communication. Future agents and orchestration workflows should call the Model Service instead of calling Ollama directly.

This design supports the project goal of building a production-ready agentic environment with strong harnessing around weaker local models.

The core rule established in this sprint is:

```text
Application logic and agents must not directly depend on Ollama.
They must communicate through the Model Service abstraction.
```

---

## Provider Interface

A `ModelProvider` interface/protocol was created.

The provider interface defines the required behavior for any model backend:

* `generate()` for complete non-streaming model responses
* `stream()` for streaming responses
* `embed()` for embeddings
* `health()` for provider health checks

This interface allows the platform to support Ollama now and vLLM later without changing future agent code.

---

## Request and Response Schemas

Typed request and response models were implemented for the Model Service.

Implemented schema categories include:

* Chat messages
* Chat/generation requests
* Chat/generation responses
* Streaming chunks
* Embedding requests
* Embedding responses
* Usage metadata
* Provider health responses

The schema layer enforces valid input before requests reach the model provider. This is an important part of the system's agent harnessing strategy.

---

## Ollama Provider

An Ollama provider implementation was added.

The Ollama provider is responsible for translating internal Model Service requests into Ollama API calls. It is the only backend component that should know Ollama-specific request and response formats.

Implemented Ollama capabilities include:

* Chat generation
* Streaming chat responses
* Embeddings
* Provider health checks
* Response parsing
* Usage metadata extraction when available
* Timeout handling
* Retry handling
* Structured provider logging

The development chat model is configured as:

```text
qwen3:4b
```

The development embedding model is configured as:

```text
nomic-embed-text-v2-moe
```

The production target can later switch to a larger model such as `qwen3:8b` without changing the application-facing Model Service interface.

---

## Non-Streaming Generation

The Model Service supports complete non-streaming generation.

A request containing role-based messages can be passed to the service, and the service returns a structured response containing:

* generated content
* model name
* provider name
* latency
* optional usage metadata
* optional raw provider response

Using chat-style messages instead of a plain prompt prepares the system for future agent prompts, system messages, orchestration context, and multi-turn interactions.

---

## Streaming Responses

Streaming response support was implemented.

The backend exposes streaming through newline-delimited JSON for Sprint 1 testing. This keeps the implementation simple and API-testable while preserving a path toward future Server-Sent Events, WebSockets, or frontend streaming interfaces.

Streaming support is important for later student-facing interactions because local models may have noticeable response latency.

---

## Embedding Support

Embedding support was added through the Model Service.

This sprint only implemented the embedding abstraction and Ollama embedding call. It did not implement RAG, document chunking, pgvector storage, or retrieval logic. Those features belong to later sprints.

This keeps Sprint 1 focused while preparing the platform for the future Knowledge Base & RAG sprint.

---

## Model Health Endpoint

A model provider health check was implemented.

The health check allows the backend to verify whether the configured model provider is reachable and whether the service can communicate with Ollama.

This is useful for local development, Docker Compose validation, and future deployment checks.

---

## FastAPI Testing Endpoints

Temporary/internal FastAPI endpoints were added for Sprint 1 validation:

```text
GET  /model/health
POST /model/generate
POST /model/embed
POST /model/stream
```

These endpoints are intended for API testing with tools such as Bruno, Postman, or curl.

They are not the final student-facing API. Future student interaction should go through the LangGraph orchestrator and agent workflow, not directly through `/model/*` endpoints.

---

## Error Handling

Structured model service exceptions were introduced.

Implemented error categories include:

* unsupported provider
* provider unavailable
* timeout
* generation failure
* embedding failure

Provider-specific errors are converted into controlled platform-level errors. This prevents raw HTTP or Ollama exceptions from leaking into future agents or API responses.

---

## Retry and Timeout Handling

Timeout and retry behavior was added for model provider requests.

The Model Service configuration now supports:

* request timeout
* maximum retries
* retry backoff

This improves robustness when the local model provider is slow to start, temporarily unavailable, or under load.

---

## Structured Logging

Structured logging was added around model operations.

Logged model events include:

* generation start
* generation completion
* streaming start
* streaming completion
* embedding start
* embedding completion
* provider metadata such as model name, provider name, latency, and message/text counts

This extends the Sprint 0 logging foundation and prepares the system for later evaluation and observability work.

---

## Docker Compose Ollama Wiring

The backend was wired to an Ollama container through Docker Compose for local development.

The backend communicates with Ollama through the Docker service name:

```text
http://ollama:11434
```

This confirms the intended local-first architecture for Phase 1:

```text
Backend Container -> Ollama Container
```

The system remains compatible with local non-Docker development by using:

```text
http://localhost:11434
```

when the backend runs outside Docker.

---

## Unit Tests

Unit tests were added for the Model Service layer.

Test coverage includes:

* schema validation
* custom exceptions
* service facade delegation
* provider factory behavior
* provider helper behavior
* FastAPI model routes using mocked services

Real Ollama calls are not required for normal unit tests or CI. This keeps automated tests deterministic and avoids depending on local model availability.

# Architectural Decisions

Several important architectural decisions were finalized during Sprint 1.

## Model Service as Boundary

The Model Service is the boundary between application logic and model providers.

Future agents, LangGraph nodes, RAG components, and context engineering modules should not call Ollama directly.

---

## Provider Independence

The system is designed around a provider interface rather than a specific model backend.

Ollama is the first implemented provider. vLLM is planned for future scaling but was intentionally not implemented in this sprint.

---

## Chat-Style Message Format

The Model Service uses role-based messages instead of a single raw prompt string.

This decision supports future agent prompts, system instructions, context injection, and multi-turn learning interactions.

---

## Local-First Model Execution

The system is designed to run with local models first.

This supports the project requirement that student data, prompts, logs, and model interactions remain local during Phase 1.

---

## Weak-Model Harnessing

The Model Service contributes to weak-model harnessing by enforcing:

* typed request and response contracts
* low default temperature
* explicit model configuration
* structured error handling
* retry and timeout behavior
* provider isolation
* logging around all model calls

This ensures that the system does not rely on the model being highly capable or perfectly reliable.

# Configuration

The following model-related configuration values were introduced:

```env
MODEL_PROVIDER=ollama
OLLAMA_BASE_URL=http://ollama:11434
OLLAMA_CHAT_MODEL=qwen3:4b
OLLAMA_EMBEDDING_MODEL=nomic-embed-text-v2-moe
MODEL_REQUEST_TIMEOUT_SECONDS=60
MODEL_MAX_RETRIES=2
MODEL_RETRY_BACKOFF_SECONDS=0.5
MODEL_TEMPERATURE=0.2
```

For local development outside Docker, `OLLAMA_BASE_URL` can be changed to:

```env
OLLAMA_BASE_URL=http://localhost:11434
```
